# ТЗ: Система оценки персонала (площадка Кингисепп) — v0.2

## 1. Цель

Веб-приложение для оценки линейного персонала ОП. Пилот: **Кингисепп (ВСМ)**.
Замена Excel-процесса: списки, анкеты, реестр, контроль тарифа (ЧСТ).

## 2. Роли

| Роль | Код | Права |
|------|-----|--------|
| Администратор системы | `admin` | Все ОП, справочники, пользователи |
| Администрация ОП | `admin_op` | В рамках своей ОП: сотрудники, назначения, dual-оценка, импорт Excel, реестр |
| Мастер | `master` | Свой список, анкета (если он primary/secondary) |
| Производитель работ | `foreman` | Аналогично мастеру |
| Начальник участка | `site_chief` | Ввод коэффициента выработки (Квыр), без анкеты рабочего |

## 3. Источники данных

| Канал | Назначение |
|-------|------------|
| Excel-импорт | Массовые изменения (База, пользователи, карнет) |
| UI Админ_ОП | Точечный ввод/правка сотрудников, назначения, dual, **срочная оценка** |

Оба канала пишут в **одну БД**. Импорт даёт отчёт «добавлено / обновлено / ошибки».

### 3.1. База сотрудников (обязательный контур)

**База = полный реестр людей ОП в системе**, не «только выгрузка 1С».

В Базе должны быть **все**, кого Администрация:
- загрузила из Excel / 1С, **или**
- внесла вручную в UI.

| Источник | Действие |
|----------|----------|
| Импорт `01_База_1С.xlsx` | upsert по `tab_no` |
| Карточка «Добавить сотрудника» (Админ_ОП) | создание/правка записи в Базе |
| Кандидат → трудоустроен | Админ_ОП заводит/обновляет в Базе нормальный `tab_no` + ФИО и далее может запускать оценку |

Карнет и оценки ссылаются **только** на записи Базы (кроме временного пула кандидатов до трудоустройства — см. 4.2–4.3).

### Файлы импорта

- `01_База_1С.xlsx` — кадры ОП (массово)
- `02_Пользователи.xlsx` — учётки ЛК
- `03_Карнет.xlsx` — пул оценки + primary-оценивающий
- `04_Квыр.xlsx` — коэффициент (или ввод в UI)
- `05_Анкеты.xlsx` — только шаблон UI (не данные)

## 4. Модель оценки (ключевое)

**По умолчанию** у сотрудника в периоде **один** оценивающий (`primary`): Мастер **или** ПР.

**Вторая оценка (dual):** только если `admin_op` включил `dual_enabled` и назначил `secondary` (другая роль/человек).

| Режим | Условие закрытия в реестр | Итог (базовая формула) |
|-------|---------------------------|-------------------------|
| Single | primary подтвердил анкету | `avg_primary × k_vyr` |
| Dual | primary + secondary подтвердили | `((avg_m + avg_f) / 2) × k_vyr` |

### 4.1. Нет primary = ожидание назначения (не ошибка)

Сотрудник может быть в карнете **без** мастера/ПР: межвахта, дома, ещё не вышел на ОП.

| Состояние | `primary` | `evaluate` | Кто действует |
|-----------|-----------|------------|---------------|
| На межвахте / ждёт назначения | пусто | `no` | никто не видит в списках оценки |
| Приехал на ОП | Админ_ОП назначает Мастера **или** ПР | Админ_ОП ставит `yes` | primary заполняет анкету |

- Пустой primary при импорте — **допустимо**, не блокирует загрузку.
- В ЛК мастера/ПР попадают только `evaluate=yes` **и** назначенный им primary/secondary.
- `site_chief` / Admin не назначаются оценивающими анкеты.

### 4.2. Кандидаты — пока не оценивать

`tab_no = Кандидат` (или статус «Кандидат») — человек **ещё официально не трудоустроен**.

| Поле | Значение |
|------|----------|
| `evaluate` | `no` (плановая оценка периода) |
| Плановый primary / dual | не назначать |
| В Базе | может ещё не быть **до** оформления |

Как только Админ_ОП оформляет человека (вручную или после появления в выгрузке 1С) — он **обязан появиться в Базе** с нормальным `tab_no`. Дальше доступны плановая и **срочная** оценка (4.3).

### 4.3. Срочная (точечная) оценка

Сценарий: вчера кандидат / не в периоде, **сегодня нужно срочно оценить**.

Админ_ОП:
1. Убеждается, что человек есть в **Базе** (если только что трудоустроен — сначала создаёт/обновляет карточку в Базе).
2. Запускает действие **«Срочная оценка»**.
3. Назначает **одного или нескольких** оценивающих (Мастер и/или ПР, список 1…N).
4. Система сразу кладёт задачу в ЛК каждого назначенного (пометка «Срочно»).

| Параметр | Правило |
|----------|---------|
| Кто назначает | только `admin_op` |
| Число оценивающих | ≥ 1, верхняя граница — по необходимости (не только dual) |
| Слепота | оценивающие не видят баллы друг друга |
| Плановый период | срочная может идти **вне** или **внутри** текущего периода; в реестре помечается `urgent` |
| Итог | среднее арифметическое **сданных** анкет по этой срочной заявке (× Квыр, если Квыр уже есть / когда появится) |
| Закрытие | Админ_ОП может закрыть заявку, когда сданы все назначенные **или** принудительно по уже сданным |

Это отдельно от обычного dual: dual — штатная вторая роль в периоде; срочная — разовая рассылка на выбранных людей.

- Пока dual выключен — secondary не видит сотрудника в плановом списке.
- Оценки друг друга не видят (слепота в dual и в срочной).

Шкала анкеты: 5 критериев × 1–5 + комментарий.
Средняя анкеты = среднее арифметическое 5 баллов.

Критерии: качество/надёжность; дисциплина; ОТ и ТБ; проф. знания; универсальность/обучаемость.

## 5. Сущности (логика БД)

- **Organization** — ОП (Кингисепп)
- **Employee (База)** — полный реестр: tab_no, fio, …; источники: импорт 1С **и** ручной ввод Админ_ОП
- **User** — tab_no, role, site, status, password_hash
- **EvaluationPeriod** — например `2026-H2`
- **Assignment** — employee + period + site + primary_* + dual_enabled + secondary_* + evaluate
- **UrgentEvaluationRequest** — employee + created_by admin_op + list of evaluators (1…N) + status + mark urgent
- **Evaluation** — привязка к Assignment **или** UrgentRequest + evaluator + role + 5 scores + comment + status
- **AssignmentDelegation** — original_primary → substitute_primary, period/from–to, reason, created_by admin_op
- **DomainEvent** (event log) — append-only журнал всех значимых действий (см. §8.3)
- **ProductionCoeff** — period + (employee \| site) + coeff + site_chief
- **RegistryRow** — снимок/view итога (флаг `urgent` при необходимости)
- **ListTicket** — «ошибка в списке» от мастера/ПР

Ключ связи: `tab_no`. ФИО — контроль при импорте (несовпадение → ошибка строки).

### 5.1. Замещение primary (делегирование)

Проблема: мастер на больничном/отпуске — список «висит», период не закрывается.

| Механизм | Описание |
|----------|----------|
| Кнопка Админ_ОП «Заместить на период» | Назначить временного primary; история original сохраняется |
| Эскалация | Если primary не заходил **N дней** (по умолчанию 3) при открытых анкетах — уведомление/очередь Админ_ОП |
| Слепота | Заместитель **не видит** черновики и сданные оценки предшественника |
| Синхронизация | Черновики старого primary в offline-кэше при конфликте → сценарий §8.1 |

После окончания замещения primary возвращается; сданные заместителем оценки остаются в истории с его `evaluator_id`.

## 6. Процесс

1. Админ_ОП загружает/обновляет Базу и Пользователей (Excel) и/или вносит людей в Базу вручную.
2. Загружает Карнет и/или правит назначения в UI (часть людей без primary — норма).
3. Открывает период оценки.
4. По мере приезда на ОП: Админ_ОП назначает primary и включает `evaluate`.
5. Primary подтверждает список → заполняет анкету → отправляет.
6. При необходимости Админ_ОП включает dual и назначает secondary → вторая анкета.
7. **Срочно:** вчерашний кандидат сегодня в Базе → «Срочная оценка» → 1…N мастеров/ПР.
8. Нач. участка вводит Квыр.
9. Система считает реестр, историю, умные комментарии (стаж × средняя), подсветку ЧСТ (≥ 6 мес. без обновления ставки).

## 8. Нефункциональные и архитектурные требования

### 8.0. Стек UI/API (решение)

- Клиент мастера/ПР: **сразу PWA (React или аналог)**, не серверные шаблоны как основной UI площадки.
- Backend: FastAPI + PostgreSQL.
- Паттерн **BFF** (Backend-for-Frontend) — разные фасады API под разные клиенты:

| BFF | Назначение | Особенности |
|-----|------------|-------------|
| Mobile/Field API | Мастер/ПР на объекте | Минимум полей, ETag/версионирование, агрессивный кэш, sync queue |
| Admin API | Админ_ОП | Тяжёлые фильтры, импорты, экспорты, замещения |
| Registry API | Реестр / HR | **Read-only**, при росте — read-replica; тяжёлый отчёт не должен ложить field API |

Пароли из Excel при импорте сразу в hash; open text в БД не хранить.

### 8.1. Offline-first PWA (критично для объекта)

**Проблема:** на ВСМ/СК связь нестабильна; заполненная в поле анкета может не отправиться и потеряться.

**Решение:**
- Фронт мастера/ПР — Progressive Web App (installable).
- Список сотрудников и черновики анкет — в **IndexedDB**.
- Работа **офлайн**: заполнение, сохранение черновика локально.
- При появлении сети — **автосинхронизация** очереди (outbox).
- Идемпотентность submit по `client_mutation_id`.

**Конфликт-резолюция:** если Админ_ОП изменил назначение (primary/dual/замещение), пока мастер писал анкету офлайн:
1. Синк получает конфликт (версия assignment / evaluator не совпала).
2. UI показывает **diff** (что изменилось на сервере).
3. Предлагает: перезаполнить / отменить локальный черновик (данные старого черновика сохраняются в event log как `draft_discarded_conflict`, не как принятая оценка).

Без offline-first процесс встаёт в «мёртвых зонах» объекта — для пилота это **must-have**, не phase-2.

### 8.2. Делегирование и замещение

См. §5.1. В UI Админ_ОП — кнопка «Заместить на период»; опционально правило эскалации при N днях без входа.

### 8.3. Event sourcing / журнал событий (аудит)

Аудит не только назначений и dual: **оценки — чувствительные данные**.

Хранить append-only поток событий, например:

```text
[14:00] Мастер_Иванов открыл анкету Сидорова
[14:05] score_quality: null → 4
[14:06] score_quality: 4 → 3
[14:07] Нажал «Отправить»
[14:08] Админ_ОП включил dual, назначил Прораб_Петрова
[14:30] Прораб_Петров отправил анкету
[15:00] Админ_ОП заместил primary Иванов → Сидоров_зам (до даты)
```

**Зачем:** споры («я не ставил двойку»), разбор bias (систематическое завышение/занижение), расследование offline-конфликтов.

Текущее состояние анкеты/назначения можно хранить в обычных таблицах (projection); **истина для разбора** — журнал событий. MVP: писать события по всем мутациям оценок, назначений, dual, срочных, замещений, импортов; UI просмотра ленты — у Админ_ОП.

### 8.4. Прочее

- Адаптив (телефон/планшет).
- HTTPS, service worker, обновление PWA без потери outbox.
- Раздельные rate-limit / таймауты для Field vs Admin vs Registry API.

## 9. Пилот — out of scope

- API прямой из 1С (пока Excel)
- Несколько ОП в одном UI (закладка org_id)
- SMS/OTP

## 10. Критерии готовности MVP

- [ ] Импорт 01/02/03 с отчётом ошибок
- [ ] База = импорт + ручной ввод Админ_ОП; все внесённые есть в Базе
- [ ] Админ_ОП меняет участок/primary и включает dual в UI
- [ ] Single-оценка до реестра
- [ ] Dual-оценка вслепую
- [ ] **Срочная оценка:** кандидат→База → 1…N оценивающих → реестр с флагом urgent
- [ ] **PWA offline:** черновик в IndexedDB + автосинк + конфликт назначения с diff
- [ ] **Замещение primary** на период + эскалация «не заходил N дней»
- [ ] **Event log** по оценкам/назначениям + просмотр ленты у Админ_ОП
- [ ] BFF: field / admin / registry API разделены
- [ ] Квыр + итоговая формула + экспорт реестра
- [ ] Подсветка просроченной ЧСТ (когда заполнят rate_updated_at)

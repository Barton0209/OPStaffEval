# Аудит System_Ocenok / KingiseppApp

Дата: 13 сентября 2026 года. Основание: архив `System_Ocenok.zip`, ТЗ из `Вставленный текст(1).txt`, пять изображений Фото1–Фото5.

**Вывод: frontend собирается, но текущую версию нельзя считать готовой к многопользовательской эксплуатации.** Подтверждены чтение файлов вне каталога сайта без авторизации, обход ограничения ролей через импорт, сохранение старой сессии после административной смены пароля и изменение уже отправленной оценки. Новое ТЗ реализовано частично.

Исходный код не исправлялся. Сборка выполнялась в извлечённой копии; проверки API — на искусственных данных в отдельной базе. Переданная рабочая база открывалась только для чтения. Секреты и персональные данные в отчёт не включены. Пути ниже указаны относительно `KingiseppApp/`, номера строк относятся к присланному исходному коду.

## 2. Дефекты, требующие исправления

### F01 — Критично: чтение файлов сервера без авторизации

**Место:** `backend/app/main.py`, строки 198–217, особенно 212–214.

SPA fallback соединяет `dist` и пользовательский URL, затем отдаёт любой существующий файл. Проверки, что итоговый путь остаётся внутри `dist`, нет. Закодированные сегменты перехода к родительскому каталогу позволяют выйти за его пределы.

**Подтверждение:** создан безвредный `frontend/audit_public_marker.txt`, вне `dist`. Неавторизованный TestClient получил его содержимое с HTTP 200. После проверки маркер удалён. Секретные файлы таким способом не запрашивались.

**Последствия:** потенциально доступны конфигурация, исходники и база, если процесс имеет права чтения и путь известен. Дефект действует при наличии собранного `dist`; поведение конкретного внешнего прокси отдельно не проверялось.

**Исправить:** раздавать статические файлы через безопасный обработчик, а fallback ограничить `index.html`. Если произвольная раздача необходима — разрешать только нормализованные пути внутри разрешённого корня с учётом symlink. Добавить негативные проверки URL с обходом каталога. Это первый блокирующий дефект.

### F02 — Критично: admin_op повышает права через Excel-импорт

**Место:** `backend/app/api/admin.py`, строки 194–244; `backend/app/services/imports.py`, ROLE_MAP и `import_users`, строки 88–101, 205–266.

Ручные создание/редактирование пользователя запрещают admin_op назначать `admin`. Импорт доступен admin_op, распознаёт роль `admin` и напрямую присваивает её пользователю. Политика прав на уровне сервиса импорта отсутствует.

**Подтверждение:** тестовый admin_op загрузил Excel со своей строкой и ролью `admin`; API ответил 200, роль в тестовой БД стала `admin`.

**Исправить:** единая проверка допустимых изменений для ручного ввода и импорта. Передавать в импорт контекст действующего пользователя; admin_op не должен создавать/изменять системного администратора или менять собственные привилегии через файл. Проверять весь пакет до применения.

### F03 — Важно: административный сброс пароля не отзывает токены

**Место:** `backend/app/api/admin.py`, `patch_user`, строки 931–932; `backend/app/deps.py`, проверка `tv`.

Изменяется только `password_hash`. `token_version` не увеличивается; обязательная смена временного пароля также не включается. Самостоятельная смена пароля использует другой путь и не устраняет эту ошибку.

**Подтверждение:** после установки нового пароля администратором прежний Bearer-токен продолжил получать `/api/field/me` с HTTP 200.

**Исправить:** увеличивать token_version при каждом сбросе/смене пароля. Для выдачи временного пароля включать must_change_password; для нового сценария первого входа явно проектировать отдельное состояние настройки пароля. Старый токен после сброса должен получать 401.

### F04 — Важно: отправленную оценку можно переписать

**Место:** `backend/app/api/field.py`, `save_assignment_evaluation`, строки 564–565 и ветка `else: ev.status = draft` перед commit.

Запрет действует лишь при повторном `submit=true`. Запрос `submit=false` изменяет баллы и переводит уже отправленную анкету в черновик. Блокировка формы в UI не защищает API.

**Подтверждение:** у тестовой отправленной анкеты баллы изменены с 4 на 1, статус — с submitted на draft; HTTP 200.

**Исправить:** запрещать любое изменение submitted обычным путём. Корректировку выделить в отдельное административное действие с причиной и сохранением предыдущей редакции. Проверить аналогичный сценарий срочной анкеты: её обработчик также не содержит отдельной блокировки submitted, пока задача ещё открыта.

### F05 — Важно: реестр не изолирован по организации пользователя

**Место:** `backend/app/api/registry.py`, `_collect` (135), `registry_rows` (220); аналогичный шаблон встречается в `backend/app/api/admin.py`, например dashboard.

Период выбирается по глобальному `settings.org_code`, а не по организации вошедшего пользователя. `_collect` фильтрует назначения по этому периоду, но не по `user.organization_id`. Проверка отдельных карточек не закрывает утечку через списки и выгрузки.

**Подтверждение:** admin_op второй искусственной организации получил строку сотрудника первой через `/api/registry/rows`.

**Исправить:** вычислять организацию и период из текущего пользователя; проверять область доступа во всех списках, статистике, импортах и выгрузках. При текущем развёртывании с одной организацией риск ограничен, но модель и ТЗ предусматривают расширение. Общая тарифная сетка также не имеет organization_id — следует явно решить, является ли она корпоративной или отдельной для ОП.

### F06 — Важно: конфликт версий блокирует офлайн-очередь

**Место:** `backend/app/api/field.py`, строки 527–535; `frontend/src/api/shared.ts`, `request`; `frontend/src/api/field.ts`, `apiSaveEvaluation`; `frontend/src/offline.ts`, строки 37–55.

Backend возвращает HTTP 409. `request` превращает его в обычное исключение, тогда как UI и outbox ждут успешный объект с `conflict=true`. `flushOutbox` ловит любое исключение как отсутствие сети и прерывает обработку. Конфликтный элемент остаётся первым и блокирует следующие; модальное окно сравнения не получает структурированные данные.

**Основание:** подтверждённый штатным тестом ответ 409 и прослеженный путь frontend. Браузерная очередь отдельно не запускалась.

**Исправить:** единый контракт 409 со структурированным diff; различать конфликты, 401/403, валидацию и сетевые сбои. Конфликтные записи сохранять для решения пользователем, а независимые записи продолжать отправлять. Не удалять введённые баллы молча.

### F07 — Важно: офлайн-данные не привязаны к пользователю и серверу

**Место:** `frontend/src/offline.ts`, строки 4–34; `frontend/src/api/shared.ts`, `clearSession`; `frontend/src/main.tsx`, `logout`.

Одна IndexedDB `kingisepp_offline`, у записи нет owner/user/organization/server. При выходе очищаются только данные сессии. Следующий пользователь отправляет старую очередь со своим токеном. При наличии общих полномочий оценка может быть записана от другого человека; иначе очередь остановится на отказе доступа. Смена адреса сервера создаёт аналогичный риск совпадения идентификаторов.

**Исправить:** ключ очереди должен включать сервер, организацию и пользователя. Отправлять только записи владельца; при выходе сохранять их изолированно и показывать число неотправленных анкет. Не решать проблему безусловным удалением очереди.

### F08 — Важно: реальные ограничения БД слабее модели и тестов

**Место:** `backend/app/models.py`, Evaluation; `backend/alembic/versions/2cf3afa55a9d_initial_schema.py`, строка 222; `backend/tests/conftest.py`.

Модель задаёт `client_mutation_id` как unique и содержит составной индекс assignment/evaluator/status. Миграция создаёт индекс mutation_id с `unique=False`; составной индекс отсутствует. Последующие миграции это не исправляют. Тесты строят схему через `Base.metadata.create_all`, поэтому проверяют другую структуру, чем установленное приложение.

**Подтверждение:** расхождение найдено и в присланной рабочей БД, и в новой БД после `alembic upgrade head`. Дубликатов по паре assignment/evaluator в переданных 10 оценках нет; это не доказательство защищённости от гонок.

Дополнительно идемпотентный поиск в `field.py` выполняется только по client_mutation_id, без привязки к пользователю/назначению, а версия назначения необязательна. Реальных гонок при одновременной записи в этом аудите не моделировали.

**Исправить:** отдельная миграция после проверки существующих дубликатов; определить область уникальности ключа операции. Ограничить поиск идемпотентности владельцем и целью, проверять совпадение операции. Часть интеграционных тестов запускать на схеме из Alembic, с включёнными внешними ключами. Сериализацию конкурентного редактирования проверять транзакционно.

### F09 — Важно: импорт 1С не соответствует ТЗ и может повредить значения

**Место:** `backend/app/services/imports.py`, `import_base`, строки 123–202.

Импорт читает активный лист и старый порядок колонок без проверки заголовков.

| Поле | ТЗ | Сейчас читается |
|---|---|---|
| Территория | N | D — номер удостоверения в новом формате |
| Подразделение | F | E — организация |
| Должность | G | F — подразделение |
| Дата приёма | K | G — должность |
| Состояние | I | H — разряд |
| ЧТС | В этом файле не задана | J — график работы, преобразуется в float |
| Дата увольнения | L | Не обрабатывается |

**Подтверждение:** синтетическая строка по ТЗ с графиком «Вахта» приводит к `ValueError` на строке 176 и HTTP 500. При пустом J ошибочная раскладка может пройти молча. Кроме того, повторный импорт старого формата присваивает hourly_rate даже при пустой ячейке и способен затереть ЧТС, введённую экономистом.

**Исправить:** явный лист `1С`, проверка схемы и сопоставление заголовков до записи. Разделить владение кадровыми полями и ЧТС. Сначала сформировать предварительный результат импорта и ошибки, затем применять транзакцию. Архивирование и испытательный срок добавить по согласованным правилам.

### F10 — Важно: каждый запуск повторно импортирует Excel

**Место:** `start.bat`, строка 34; `backend/scripts/init_db.py`, `main(do_import=True)`; `backend/app/services/imports.py`, import_base/import_carnet/import_users.

`start.bat` вызывает init_db без `--no-import`. Запуск сервера снова читает файлы и обновляет данные. Старые Excel могут перезаписать изменения из интерфейса: кадровые поля, ЧТС, назначения и роли. Если обязательных файлов нет, запуск прерывается даже при существующей базе.

**Исправить:** отделить одноразовую инициализацию и явный импорт от обычного запуска. На штатном старте выполнять проверку конфигурации, резервирование, миграции и запуск приложения. Ошибку резервирования обрабатывать явно: сейчас start.bat продолжает работу независимо от её результата.

### F11 — Важно: шаблонный SECRET_KEY проходит проверку

**Место:** `.env.example`, строка 9; `setup.bat`, создание .env; `backend/app/config.py`, model_post_init.

Установщик копирует пример, а проверка секрета оценивает только непустоту и длину. Известная строка-заглушка длиннее 32 символов принимается.

**Подтверждение:** Settings с ключом из шаблона успешно создаётся. В переданном .env находится другая строка длиной 64 символа — использование шаблона в текущей установке не утверждается.

**Исправить:** генерировать уникальный ключ при новой установке, запрещать известные заглушки. Не перегенерировать существующий ключ при обычном старте. Прямой bootstrap в main.py также создаёт временные пароли без реальной выдачи, хотя журнал сообщает «Пароль выдан отдельно»; нужен единый управляемый способ первичной выдачи.

### F12 — Важно: конфигурации LAN и Android расходятся

**Место:** `Caddyfile`; `frontend/capacitor.config.ts`, строки 7–12; `.env.example`, строка 17; `backend/app/main.py`, CORSMiddleware.

Caddy настроен на HTTP :8080. APK запрещает cleartext/mixed content и использует схему https. CORS допускает `capacitor://localhost`, но не `https://localhost`, соответствующий указанной Android-схеме. Это конфигурационное расхождение; фактический Origin APK следует проверить на устройстве.

Отдельно CORS не раскрывает `X-New-Token` и `X-Require-Password-Change`. При cross-origin запросе JavaScript не сможет прочитать эти заголовки, даже когда сам запрос разрешён. Отсутствие expose_headers подтверждено тестом.

**Исправить:** единый HTTPS-адрес с доверенным клиентами сертификатом, точный список Origin веба/APK, раскрытие двух служебных заголовков. Проверить вход, смену пароля, продление токена и скачивание файлов на реальном Android. Заголовок HSTS не шифрует текущий HTTP-канал.

### F13 — Средний приоритет: реестр выполняет тысячи запросов

**Место:** `backend/app/api/registry.py`, `_collect`; `backend/app/services/evaluations.py`, assignment_registry_status/covering_evaluator_ids; `backend/app/api/economist.py`, list_employees.

В цикле по назначениям отдельно запрашиваются оценки, замещения и коэффициенты. Наличие joinedload для Employee этого не устраняет. В форме экономиста тарифные границы также вычисляются с обращением к БД для каждого сотрудника.

**Подтверждение:** 455 строк реестра — 2 239 запросов. Время 0,505 с относится только к локальному измерению на чтении и не является прогнозом Windows-сервера или нагрузочным тестом.

**Исправить:** загрузить оценки/коэффициенты/замещения пакетно, построить словари, фильтровать область доступа в SQL. Ввести пагинацию там, где нужен просмотр, и отдельный управляемый поток экспорта. После этого измерить работу нескольких пользователей; менять SQLite только на основании требований и нагрузки.

### F14 — Средний приоритет: импорт блокирует event loop и преждевременно заменяет файл

**Место:** `backend/app/api/admin.py`, async import_upload/import_daily_assignees_file/import_tariff_grid_file.

Синхронные pandas/openpyxl/SQLAlchemy выполняются непосредственно внутри async обработчиков. В однопроцессном сервере длительный импорт задерживает другие запросы. Загруженный файл записывается под постоянным именем до успешного разбора и проверки данных. Неудачная загрузка заменяет прошлый источник; последующий запуск повторит импорт повреждённого файла. Пакетный import/all фиксирует каждый импорт отдельно, поэтому не атомарен целиком.

**Исправить:** временные уникальные файлы, предварительная проверка, понятная транзакционная граница; замена источника только после успеха. Тяжёлую обработку вынести в рабочий поток/задачу с отдельной SQLAlchemy-сессией. Ограничение ZIP ratio уже есть; дополнительно нужен предел суммарного распакованного объёма и понятный ответ 400 на некорректный архив.

### F15 — Средний приоритет: источники истории и права расходятся с требованиями

**Место:** `backend/app/api/admin.py`, upload/tariff-grid; `backend/app/api/economist.py`; `backend/app/scheduler.py`, cleanup_events_job; `backend/app/services/imports.py`, import_ud_rates/import_base.

Экономист не имеет API загрузки УД и сетки. Тарифную сетку разрешено загружать только admin_op, даже admin не входит в эту зависимость. Это противоположно новой матрице. При этом существующие тесты закрепляют часть старого поведения — обновить только UI недостаточно.

История ЧТС записывается при ручной операции экономиста, но импорты меняют поля ставки без единого журнала RateHistory. DomainEvent автоматически удаляется через 90 дней; использовать его как постоянную историю загрузок и изменений нельзя.

**Исправить:** согласовать матрицу ролей, применять её во всех путях изменения данных. Ввести единый сервис изменения ЧТС и отдельный долговременный журнал импорта с исходным именем файла, датой, пользователем, результатом и версией схемы.

## 4. Зависимости

`npm audit` по присланному lock-файлу сообщает три moderate для цепочки `@capacitor/cli → xcode → uuid`. Это одна исходная advisory и два зависимых пакета, а не три независимых дефекта приложения. Пакеты находятся в инструментах сборки; эксплуатация через пользовательский frontend этим не доказана.

Для uuid речь о проверке границ внешнего буфера в v3/v5/v6. Официальное уведомление: [GHSA-w5hq-g745-h8pq](https://github.com/uuidjs/uuid/security/advisories/GHSA-w5hq-g745-h8pq). Не следует автоматически применять `npm audit fix --force`: он предлагает изменение версии Capacitor CLI. Обновление выбирать совместно с проверкой Android-сборки.

Python requirements преимущественно задаёт нижние границы `>=`, поэтому новая установка получает другие версии; lock-файла Python в проверенном проекте не найдено. Это уже наблюдается при аудите. Зафиксировать проверенный набор и отдельные зависимости тестирования. npm-установку для воспроизводимого выпуска выполнять по lock-файлу. Полный вывод Python vulnerability scan в этот аудит не входит.

## 5. Рекомендуемый порядок работ

1. Закрыть F01 и F02; проверить отказ на обход пути и повышение роли через импорт. Если сервер уже был доступен, проверить журналы и оценить необходимость смены ключей и учётных данных исходя из фактической доступности, а не считать компрометацию установленной.
2. Исправить F03–F08: отзыв токенов, неизменяемость отправленных анкет, изоляцию организаций, контракт конфликта и очередь, миграции ограничений.
3. Убрать импорт из обычного старта, разделить кадровые данные и ставки; определить форматы файлов и журнал загрузок.
4. Уточнить только открытые бизнес-решения ТЗ: соответствие двух ИТР-групп ролям, минимальные права ЦОК, критерий идентичности при повторном найме, формат формы экономиста. Для первого входа без пароля определить, как подтверждается право конкретного человека установить пароль выбранной учётной записи: одного выбора имени недостаточно против захвата ещё не активированной записи.
5. Реализовать вход «Контроль», кабинеты, архив, исторические критерии, Свод и выгрузки по фазам ТЗ.
6. Проверить выпуск на Windows и Android: чистая установка, обновление существующей БД, HTTPS, офлайн/смена пользователя, одновременное редактирование, восстановление резервной копии.

## 6. Что уже сделано удачно

Есть разделение frontend/backend, Pydantic-схемы, зависимости проверки ролей, проверки доступа к отдельным объектам, BCrypt, механизм token_version, ограничитель входа, WAL и внешние ключи, Alembic, тесты, журнал событий и экранирование опасных значений при Excel-экспорте. Резервирование использует sqlite3.backup, подходящий для согласованной копии работающей SQLite.

Переписывать проект с нуля по результатам этого аудита не требуется. Сначала необходимо устранить обходы защиты и несогласованность записи данных, затем расширять готовые части под новое ТЗ. Резервные копии сейчас находятся рядом с основной БД: такой порядок защищает от части ошибок, но восстановление после отказа диска требует отдельного места хранения и проверенного сценария восстановления.

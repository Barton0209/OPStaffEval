# Мастер-промт для AI-агента: развитие System_Ocenok / KingiseppApp

Ты — ведущий full-stack архитектор, senior-разработчик, инженер по безопасности, специалист по данным и QA-инженер. 
Твоя задача — самостоятельно изучить, безопасно доработать и довести до рабочего состояния существующий проект **System_Ocenok / KingiseppApp**, не разрушая уже работающие функции.

Работай непосредственно с проектом в:

```text
C:\My_Project\System_Ocenok
```

Основное приложение находится в каталоге `KingiseppApp`. Перед началом найди и прочитай все локальные инструкции проекта (`AGENTS.md`, `README`, документы, планы, журнал аудита), затем изучи код, структуру БД, 
миграции, тесты, установочные скрипты и текущее состояние Git. Если рядом присутствует файл `System_Ocenok_Audit.md`, считай его обязательным входным материалом: перепроверь находки и устрани подтверждённые критические 
дефекты до реализации новых функций.

## 1. Главная цель

Расширить, улучшить, упростить существующую систему оценки рабочего персонала. Система длолжна поддерживала два сценария входа:

1й существующий сейчас сценарий - для Производителей работ, Мастеров и Начальников участков. Сохрани его поведение и совместимость. 
Не переделывай работающий вход без необходимости.
И новый 2й сценарий для Руководства ОП, Администрации ОП, Экономистов ОП и подразделений ЦОК. 

Реализуй каскадный выбор площадки, отдела и пользователя, первый вход с созданием пароля, ролевые кабинеты, импорты, архив уволенных, аналитику и пакетные выгрузки.

Главный принцип системы: **каждый пользователь после входа видит и выполняет только свою работу**. Ограничения должны действовать одновременно на уровне интерфейса и backend API. 
Скрытая кнопка не является защитой: каждый защищённый endpoint обязан проверять роль, организацию, площадку, отдел, участок и принадлежность объекта в зависимости от операции.

Интерфейс должен быть простым: минимум экранов, кликов, ручных выгрузок и промежуточных подтверждений. Руководитель должен получать требуемый список и Excel не более чем за четыре понятных действия.

## 2. Текущий технологический контекст

Сохрани существующий стек, если анализ не выявит объективной несовместимости:

- Backend: Python 3.11+, FastAPI, SQLAlchemy 2.x, Pydantic, Alembic.
- База: SQLite в WAL-режиме, работа нескольких пользователей, резервные копии через `sqlite3.backup()`.
- Frontend: React 19, TypeScript, Vite.
- Мобильное приложение: Capacitor 8 / Android.
- Развёртывание: Windows batch-скрипты, локальная сеть, Caddy.
- Аутентификация: JWT HS256, Bearer token, `token_version` для отзыва старых токенов.

Не переписывай проект с нуля. Развивай существующие модели, сервисы, API и UI. Перед изменениями зафиксируй исходное состояние: текущая ветка, незакоммиченные пользовательские изменения, результат frontend-сборки и backend-тестов. Не удаляй и не перезаписывай пользовательские изменения. Не применяй разрушительные команды Git.

## 3. Обязательный порядок работы

### 3.1. Исследование

До реализации:

1. Составь карту frontend, backend, моделей, миграций, API, ролей, импортов, экспортов и скриптов запуска.
2. Найди текущие маршруты входа и ролевые guards.
3. Проверь реальную схему существующей SQLite и соответствие Alembic-моделям.
4. Запусти текущие тесты и production-сборку.
5. Найди места, где роли проверяются только в UI либо объекты выбираются без фильтра организации/площадки.
6. Изучи форматы уже существующих импортов и не предполагай, что они соответствуют новым файлам.
7. Проверь приложенные изображения визуально до встраивания.

После исследования составь краткий внутренний план по фазам, но не останавливайся ради согласования обычных технических решений. Если бизнес-правило действительно не определено, выбери безопасное и обратимое допущение, вынеси его в конфигурацию либо отдельную таблицу и явно перечисли в итоговом отчёте.

### 3.2. Безопасность перед расширением

До открытия новых функций исправь и покрой регрессионными тестами следующие классы проблем, если они присутствуют:

- traversal/выход за каталог при раздаче статических файлов;
- повышение привилегий через импорт пользователей;
- отсутствие увеличения `token_version` при сбросе или установке пароля;
- изменение анкеты после статуса `submitted` обычным пользователем;
- чтение данных другой организации, площадки или участка через списки, карточки и выгрузки;
- несогласованный контракт HTTP 409 и офлайн-очереди;
- общая офлайн-очередь для разных пользователей или серверов;
- расхождение между SQLAlchemy-моделями, Alembic и тестовой схемой;
- известный шаблонный `SECRET_KEY`, принимаемый как рабочий;
- повторный импорт Excel при каждом обычном запуске программы.

Применяй одну и ту же матрицу доступа во всех путях изменения данных: UI, API, ручное редактирование, пакетные операции и Excel-импорт. Импорт не должен обходить ограничения ручного API.

## 4. Начальный экран и два вида входа

Сохрани существующий сценарий авторизации для Производителей работ, Мастеров и Начальников участков, основанный на данных листа `Прораб_Мастер`. Сохрани существующие рабочие кабинеты и поведение офлайн-оценок. 
Проведи регрессионные тесты, чтобы новые роли и маршруты не открыли оценщикам административные функции.

Начальный экран - Используй `Фото1` как композиционный образец. Правая часть — слайдер из `Фото2`, `Фото3`, `Фото4` с автоматической прокруткой, индикаторами, ручным переключением и разумной паузой при взаимодействии. 
Левая часть — блок авторизации с `Фото5` как фоном. Обеспечь читаемость с помощью светлой подложки/оверлея и достаточного контраста.
Текст над формой:
```text
Оценка рабочего персонала ОП и контроль показателей
```
Используй корректное написание бренда **«ВЕЛЕССТРОЙ»** и организации **ООО «ВелесстройМонтаж»**. Не повторяй опечатку из макета.
Удали из новой страницы:
- переключатели «Кандидат / Сотрудник»;
- блок «Возможности личного кабинета» и весь текст о резюме и вакансиях;
- ссылку «Зарегистрироваться»;
- кнопку «Войти из корпоративной сети».
Внизу покажи:

Форма «Контроль» — каскад:

1. **Выбор площадки для входа (Territory)**. Начальное значение `------`.
2. **Выбор отдела (Role)**. Неактивно до выбора Territory; после активации значение `------`.

4. **Пароль**. Показывается только после выбора пользователя, если пароль уже установлен.

### 4.3. Первый вход и пароль

Первый вход пользователя «Контроль», у которого пароль ещё не установлен:

1. Пользователь выбирает Territory, Role и своё имя.
2. Пароль в основной форме не запрашивается.
3. После `Войти` открывается отдельная страница создания пароля: новый пароль и подтверждение, без текущего пароля.
4. После успешной установки выполняется автоматический вход в разрешённый кабинет.
5. `token_version` увеличивается; ранее выданные токены становятся недействительными.

Повторный вход требует пароль. После административного сброса пароль снова считается неустановленным, старые токены отзываются, пользователь повторяет безопасную процедуру создания.

**Не реализуй захватываемую учётную запись только по выбору ФИО.** Выбор имени не доказывает личность. Используй существующий корпоративный доверенный механизм, одноразовый код, временный секрет либо другой доступный второй фактор. 
Если такого механизма в проекте и окружении нет, реализуй временный пароль/одноразовый код, который выдаёт Администрация ОП вне интерфейса, и документируй процесс. Не выдавай одноразовый секрет в общедоступном списке или логах.

Защити login/setup/reset rate limit, аудитом событий и нейтральными ответами, которые не раскрывают лишнюю информацию. Пароли хешируй проверенной схемой. Не храни пароль в открытом виде и не помещай его в журналы.

## 5. Роли и матрица доступа

Существующие роли:

```text
admin = cok_okit
admin_op заменить/обьеденить с management_op
master
foreman
site_chief
economist
```

Добавить роли:

```text
cok_adapt
cok_otiz
```

Рабочее сопоставление отделов:

| Отдел | Системная роль | Кабинет |
|---|---|---|
| Линейный ИТР | master/foreman по импортированной группе | Анкеты подчинённых, оценки |
| Линейный ИТР2 | master/foreman по импортированной группе | Анкеты подчинённых, оценки, расширенный личный кабинет |
| Руководство ОП | management_op | Свод, итоговые анкеты и выгрузки, расширенный личный кабинет, отчеты по своей Territory |
| Администрация ОП | admin_op | Администрация и административные импорты, выполняет роль admin но только на свойе Territory, отчеты по своей Territory  |
| Экономисты ОП | economist | Экономисты и экономические импорты, внесенение УД, ЧТС и отчеты по своей Territory |
| ЦОК_ОКиТ | cok_okit | Максимальный доступ по всем Territory, режим бога |
| ЦОК_Адаптация | cok_adapt | Архив/подбор общие отчеты по своей Territory
| ЦОК_ОТиЗ | cok_otiz | Экономисты и экономические импорты, внесенение УД, ЧТС и общие отчеты по своей Territory


Не кодируй бизнес-разрешения россыпью `if role == ...`. Создай централизованную и тестируемую политику permissions/capabilities. Лист `Permission` может задавать дополнительные разрешения только в пределах верхней границы системной роли; импортированный файл не может выдать `admin` или расширить права выше допустимого шаблона.

Минимальная матрица:

| Функция | economist | admin_op | site_chief | management_op | admin |
|---|:---:|:---:|:---:|:---:|:---:|
| Административные импорты базы, ежедневного учёта, пользователей, распределения, реестров | Нет | Да | Нет | Нет | Да |
| Экономические импорты УД/ЧТС, тарифной сетки, формы экономиста | Да | Нет | Нет | Нет | Да |
| Просмотр данных, загруженных экономистом | Нет, кроме рабочей формы ввода | Да | Да, свой участок | Да, своя площадка | Да |
| Итоговые анкеты и ЧТС | Нет | Да | Да, свой участок | Да, своя площадка | Да |
| Оценки мастеров в незавершённых анкетах | Нет | Нет | Нет | Нет | Да |
| Свод | Нет | Нет | Нет | Да | Да |
| Архив уволенных и Excel | Нет | Да | Нет | По отдельному разрешению | Да |
| Полный Excel и пакет PDF | Нет | Да | Нет | Да, своя площадка | Да |
| Выставление оценки | Нет | Нет | Только если предусмотрено существующим процессом | Нет | Да как технический администратор, с аудитом |

Для ролей ЦОК сделай deny-by-default. Пока конкретные права не подтверждены, они не должны автоматически получать широкий доступ. Подготовь централизованную конфигурацию и тесты, чтобы права можно было расширить без переписывания endpoint-ов.

## 6. Кабинет Экономиста ОП

Экономист видит только вкладку **«Экономисты»** и свою вкладку загрузки в Настройках. Он не видит административные, оценочные, сводные и кадровые функции.

Реализуй загрузку утверждаемой формы со следующими ожидаемыми полями:

- табельный номер;
- ФИО;
- должность;
- разряд;
- признак «были/не были изменения»;
- ЧТС минимальная;
- ЧТС максимальная;
- при наличии — актуальная ЧТС и дата изменения.

Не привязывай импорт к позиции столбцов без проверки. Сопоставляй по нормализованным заголовкам, показывай предварительную проверку и понятные ошибки строк. Строки с изменениями выделяй цветом. Сохраняй полную историю ЧТС: старое значение, новое значение, дата, источник файла, пользователь, комментарий/причина. Данные видят только Руководство ОП, Начальники соответствующего участка и администраторы согласно матрице.

## 7. Кабинет Администрации ОП

Кнопка/раздел **«Администрация»** содержит три простые вкладки:

1. **Новые сотрудники** — загрузка и обработка новых сотрудников.
2. **Изменить прораба** — смена/замена Прораба или Мастера у существующих сотрудников с историей изменения и защитой от конфликтов версий.
3. **Уволенные** — управление архивом уволенных.

Увольнение — мягкое архивирование, а не физическое удаление:

- сотрудник исчезает из активных списков;
- сохраняются его личная карточка, все периоды работы, стаж, оценки, анкеты, ЧТС и изменения ставок;
- фиксируются дата увольнения, источник, пользователь и время операции;
- архив можно фильтровать и выгружать в Excel;
- при повторном трудоустройстве история связывается с тем же человеком и создаётся новый период занятости;
- автоматическое архивирование срабатывает при импорте Базы сотрудников, если в колонке L задана дата увольнения.

Не связывай людей только по ФИО. Используй устойчивый идентификатор: табельный номер с префиксом и предусмотренный бизнес-ключ. Если при повторном найме табельный меняется, создай механизм ручного подтверждения совпадения, не объединяй записи автоматически по одному имени.

## 8. Кабинет Начальника участка

Начальник участка видит только свой участок:

- число ожидающих анкет;
- число завершённых анкет;
- список ожидающих без баллов и комментариев Мастеров/Прорабов;
- список завершённых с табельным номером, ФИО, итоговой оценкой и разрешёнными данными ЧТС.

До окончательного завершения анкеты нельзя вернуть через API промежуточные оценки другого оценщика, даже если UI их скрывает. После завершения показывай только тот объём данных, который разрешён матрицей. Эта итоговая вкладка также доступна Руководству ОП в области его площадки.

## 9. Кабинет Руководства ОП — «Свод»

Сделай самостоятельный экран без необходимости вручную выгружать реестр и настраивать фильтры.

1. Показать список участков/отделов: Теплоизоляция, МБР, Строительные леса и другие значения из данных.
2. Клик по участку показывает число сотрудников в диапазонах итоговой оценки.
3. Начальные диапазоны: `[1,2)`, `[2,3)`, `[3,4)`, `[4,5]`.
4. Границы должны быть настраиваемыми и непересекающимися. Каждый сотрудник попадает ровно в один диапазон.
5. Клик по диапазону раскрывает список на том же экране: ФИО, табельный номер, должность, итоговая оценка, перевод на другое ОП, целевая площадка и дата перевода.
6. Кнопка `Выгрузить в Excel` скачивает именно раскрытый/отфильтрованный список.

Свод должен считать данные на сервере с обязательной областью доступа. Не передавай весь массив в браузер для последующей фильтрации, если пользователь не имеет права видеть все строки.

## 10. Вкладка «Настройка»

### 10.1. «Загрузка файлов с данными (Администрация)»

Переименуй прежний `Импорт Excel`. Каждый блок показывает:

- назначение файла;
- имя последнего успешно загруженного файла;
- дату и время загрузки в формате `DD.MM.YYYY HH:mm`;
- кто загрузил;
- результат: добавлено, обновлено, архивировано, пропущено, ошибки;
- кнопки `Выбор файла` и `Загрузить файл`.

Блоки:

1. **База сотрудников** — прежняя База 1С.
2. **Ежедневный учет**.
3. **Пользователи, роли, доступ**.
4. **Распределение сотрудников по Прорабам/Мастерам**.
5. **Реестры оценок** — отдельные слоты:
   - `2024 Реестр за 1 полугодие.xlsx`;
   - `2024 Реестр за 2 полугодие.xlsx`;
   - `2025 Реестр за 1 полугодие.xlsx`;
   - `2025 Реестр за 2 полугодие.xlsx`;
   - `2026 Реестр за 1 полугодие.xlsx`;
   - `2026 Реестр за 2 полугодие.xlsx`.

### 10.2. «Загрузка файлов с данными (Экономисты)»

Перенеси сюда:

- `УД список / ЧТС`;
- `Тарифная сетка (мин/макс ЧТС)`;
- форму обновления экономиста.

Доступ — economist и admin согласно матрице. У admin_op нет доступа к экономическим импортам, если матрица не будет явно изменена.

## 11. Форматы импортируемых файлов

### 11.1. «База сотрудников»

Обязательный лист: `1С`. Заголовки на строке 1.

| Колонка | Поле | Использовать |
|---|---|:---:|
| A | Табельный номер с префиксами | Да |
| B | ФИО | Да |
| C | Удостоверение.Серия | Нет |
| D | Удостоверение.Номер | Нет |
| E | Организация | Да |
| F | Подразделение | Да |
| G | Должность | Да |
| H | Разряд (категория) | Да |
| I | Состояние | Да |
| J | График работы | Нет |
| K | Дата приема | Да |
| L | Дата увольнения | Да |
| M | Страна гражданства | Да |
| N | Территория | Да |
| O–X | Остальные перечисленные персональные/служебные поля | Нет |

Правила:

- если от даты приёма до текущей даты прошло менее трёх календарных месяцев, статус/метка `Испытательный срок`;
- при заполненной дате увольнения сотрудник архивируется;
- импорт базы сотрудников не имеет права обнулять ЧТС и другие поля, владельцем которых является Экономист;
- сначала проверить лист, заголовки, типы, дубли и ссылки, затем применять изменения;
- импорт должен быть идемпотентным: повтор того же файла не создаёт дубликаты;
- ошибка одной строки должна отображаться с номером строки, но правила атомарности должны быть явными: критическая ошибка схемы отменяет импорт целиком.

### 11.2. «Ежедневный учет»

Лист: `ЕЖЕДНЕВНЫЙ УЧЕТ`. Заголовки на строке 5, данные со строки 6.

Использовать:

- C — Площадка;
- D — Табельный номер;
- E — ФИО;
- G — Гражданство;
- J — Фактическая должность;
- K — Участок/Отдел;
- P — Въезд в РФ/Прием на работу, дата прилёта на ОП / начала вахты.

Не использовать: A, B, F, H, I, L, M, N, O.

Если D равно `Кандидат`, `Нелегал` или `Прием` без учёта регистра и пробелов — установить метку `Кандидат`. После появления реального табельного номера и даты приёма перевести в `Испытательный срок`, если со дня прилёта на ОП ещё не прошло три календарных месяца. Разработай устойчивое сопоставление временной кандидатской записи с оформленным сотрудником и вынеси сомнительные совпадения на ручное подтверждение.

### 11.3. «Пользователи, роли, доступ»

Три обязательных листа, заголовки на строке 1:

`Group_of_Users`:

```text
Territory
Role
Group_of_Users
Permission
```

`Users`:

```text
Group_of_Users
Users
Actual_position
```

`Прораб_Мастер`:

```text
Group_of_Users
Табельный номер (с префиксами)
User
Подразделение
Actual_position
Территория
```

Первые два листа — источник каскада «Контроль». Третий — источник существующего входа «Оценка». Нормализуй пробелы и регистр для сопоставления, сохраняя исходные отображаемые значения. Не доверяй тексту Permission как неограниченной команде: разрешай только известные коды из whitelist и в рамках системной роли.

### 11.4. «Реестры оценок»

Заголовки на строке 1. Период определяется слотом импорта и проверяется по имени/метаданным, но не доверяй только имени файла.

Колонки:

- A `No`;
- B `ТАБ№`;
- C `ФИО`;
- D `ПЛОЩАДКА`;
- E `ДОЛЖНОСТЬ`;
- F `ПОДРАЗДЕЛЕНИЕ (ОТДЕЛ)`;
- G ФИО Мастера, первая оценка;
- H–S — 12 критериев первой оценки;
- T — Средняя оценка 1;
- U — ФИО Производителя работ, вторая оценка;
- V–AG — те же 12 критериев второй оценки;
- AH — Средняя оценка 2;
- AI — Коэффициент производственной выработки;
- AJ — Итоговая оценка;
- AK — служебный `Столбец1`, использовать только после подтверждения назначения.

12 критериев в порядке H–S и V–AG:

1. Фиксация терминалом при посещении работы.
2. Трудовая дисциплина.
3. Взаимодействие внутри коллектива.
4. Соблюдение охраны труда.
5. Отношение к руководству.
6. Качество выполнения работы.
7. Способность быстро менять рабочее место/деятельность.
8. Знание технологии работ.
9. Знание применяемых материалов.
10. Ответственность к работе.
11. Выполнение наиболее сложных работ.
12. Прогресс в освоении новых навыков.

Не сворачивай исторические 12 критериев в существующие 5 без утверждённого правила. Реализуй версионируемую модель набора критериев либо отдельную структуру исторического реестра. Проверяй диапазон баллов и самостоятельно пересчитывай средние/итог, сравнивая с T/AH/AJ. Расхождения показывай в отчёте импорта; исходные значения сохраняй для аудита.

## 12. Модель данных и миграции

Спроектируй нормализованную схему, совместимую с текущими данными. Предпочтительные сущности:

- `users` — пользователь, системная роль, статус, nullable password_hash для контролируемого первого входа, token_version;
- `territories`, `departments`, `groups`, связи territory-role-group-user;
- `permissions`, role permissions, ограниченные импортированные разрешения;
- `employees` — устойчивая карточка человека;
- `employments` — периоды работы, приём, увольнение, организация, площадка, участок, должность;
- `assignments` — распределение по оценщикам с версией;
- `evaluation_periods`, `criterion_sets`, `criteria`, `evaluations`, `evaluation_scores`;
- `rate_history` и тарифные сетки с областью организации/площадки;
- `transfers` — перевод на другое ОП, цель, дата, статус;
- `import_jobs` / `import_log` / `import_errors`;
- аудит значимых действий.

Можно адаптировать существующую схему вместо буквального добавления каждой таблицы, но обеспечь те же свойства: история, целостность, область доступа и возможность повторного найма.

Миграции:

1. Делай только через Alembic для постоянной схемы.
2. Не смешивай произвольные `ALTER TABLE` при старте с миграциями.
3. Миграция существующей БД обязана быть безопасной и обратимо проверяемой на её копии.
4. Перед добавлением unique constraints проверяй и разрешай существующие дубли.
5. Тестовая схема должна строиться миграциями либо регулярно сравниваться с ними.
6. Перед миграцией создавай согласованную резервную копию; исходную пользовательскую БД не удаляй.

Для SQLite оставь WAL, foreign_keys, busy_timeout. Сначала оптимизируй транзакции, индексы и N+1-запросы. Не меняй СУБД без измеренной необходимости. Проведи тест параллельной записи и документируй практический предел текущей конфигурации.

Не полагайся на claims без сверки актуального пользователя и `token_version` с БД. При изменении роли, статуса, области доступа или пароля отзывай старые сессии.

## 14. Выгрузки

Создай единый понятный раздел:

1. **Полный Excel сотрудников** — все разрешённые пользователю сведения, с фильтрами и датой формирования.
2. **Пакет PDF-анкет**:
   - фильтр площадка/участок;
   - фильтр должность;
   - поиск по ФИО и табельному;
   - выбор отдельных строк;
   - `Выделить всё` только в текущей разрешённой выборке;
   - `Скачать PDF` создаёт ZIP с PDF выбранных анкет.

Не формируй огромный архив в памяти. Используй поток/временный файл, безопасные имена и ограничение разумного количества. В ZIP добавь manifest с периодом, фильтрами и списком анкет. Повторяющиеся имена не должны затирать файлы — включай табельный номер/ID.

## 15. Frontend и UX

- Реализуй маршруты и guards по permissions.
- При 401 завершай локальную сессию; при 403 показывай понятный отказ; при 409 отображай конфликт с действиями пользователя.
- Не теряй заполненную анкету при конфликте или кратковременной потере сети.
- Офлайн-очередь привяжи к серверу, организации и пользователю. Не отправляй запись одного пользователя под токеном другого.
- Не кэшируй API-ответы service worker-ом.
- Все новые формы должны работать с клавиатурой, иметь label, focus, disabled/loading/error states и адаптацию под телефон.
- Используй приложенные изображения оптимизированно; не растягивай с потерей пропорций. Добавь подходящий `object-fit`, responsive layout и lazy/preload по необходимости.
- Не размещай в клиенте секреты и полную матрицу как единственный источник истины.

## 16. Развёртывание, Windows и Android

- Обычный `start.bat` не должен автоматически повторно импортировать старые Excel.
- Раздели `setup`, миграции, явный импорт и ежедневный запуск.
- Для установки используй воспроизводимые зависимости: npm по lock-файлу; Python — проверенный lock/constraints.
- Генерируй уникальный `SECRET_KEY` при первой установке; запрещай известные заглушки.
- Не продолжай запуск при неуспешной миграции или критическом сбое резервного копирования.
- Согласуй Caddy, CORS и Capacitor с единым HTTPS-сценарием. HSTS не заменяет TLS.
- Проверь реальные Origin и чтение служебных заголовков токена в Android WebView.
- Не применяй `npm audit fix --force` автоматически. Обновления Capacitor проверяй совместно со сборкой APK.
- Не коммить `.env`, БД, резервные копии, реальные Excel с персональными данными, секреты и подписывающие ключи APK.

## 17. Тестирование

Добавь полезные backend, frontend и интеграционные тесты. Минимальный обязательный набор:

### Аутентификация и права

- вход «Оценка» не сломан;
- каскад «Контроль» не показывает чужие связки;
- первый вход, повторный вход и сброс пароля;
- старый JWT после сброса/смены роли получает 401;
- login/setup имеют rate limit;
- каждая роль получает разрешённые функции и 403 на запрещённые;
- admin_op не повышает себя/другого до admin через UI, API или Excel;
- пользователь другой организации/площадки/участка не читает карточки, списки, своды и экспорты.

### Оценки и офлайн

- submitted нельзя изменить обычным endpoint;
- Начальник не видит промежуточные баллы Мастера;
- 409 содержит структурированный конфликт;
- конфликтная офлайн-запись не уничтожается и не блокирует независимые записи;
- выход/вход другим пользователем не смешивает очередь;
- повторная отправка client mutation идемпотентна в правильной области пользователя и объекта.

### Импорты

- точные листы и строки заголовков;
- полный mapping столбцов каждого формата;
- плохая схема отменяет импорт;
- дубли и повторный импорт;
- кандидат → испытательный срок;
- увольнение → архив и повторный найм с историей;
- импорт базы не затирает ЧТС;
- Permission не повышает системную роль;
- формулы и подозрительные архивы безопасно отвергаются/экранируются;
- неверная строка даёт понятный номер и причину.

### Свод и выгрузки

- граничные значения 1, 2, 3, 4, 5 входят ровно в один диапазон;
- область доступа применяется на сервере;
- Excel совпадает с раскрытым списком;
- ZIP содержит выбранные PDF и manifest;
- формулы из пользовательских строк не исполняются как Excel-формулы.

### Миграции и эксплуатация

- чистая БД мигрирует до head;
- копия существующей БД мигрирует без потери основных количеств и связей;
- `PRAGMA quick_check` и `foreign_key_check` успешны;
- старт без исходных Excel работает с существующей БД;
- резервная копия реально восстанавливается;
- production frontend собирается;
- Android sync/build проходит в доступном окружении;
- smoke test нескольких параллельных чтений и записей SQLite.

Не подменяй интеграционные тесты `Base.metadata.create_all`, если production использует Alembic. Сравнивай реальную миграционную схему с metadata.

## 18. Критерии приёмки

Работа считается выполненной только если:

1. Экономист видит только свою рабочую область и разрешённую загрузку.
2. Начальник участка не получает баллы Мастеров по незавершённым анкетам ни через UI, ни прямым API-запросом.
3. Руководитель за четыре действия или меньше получает список сотрудников диапазона и Excel.
4. Первый вход «Контроль» безопасно ведёт к созданию пароля; повторный требует пароль; сброс отзывает токены.
5. Уволенный исчезает из активной базы, появляется в архиве со всей историей, выгружается в Excel и корректно связывается при повторном найме.
6. Пакет PDF по участку и должности скачивается одним ZIP.
7. Все импорты проверяют правильный лист, строку заголовков и поля; ошибочный формат не повреждает БД.
8. Импорт не может расширить права выше системной роли.
9. Обычный запуск не повторяет импорт автоматически.
10. Подтверждённые критические дефекты безопасности закрыты регрессионными тестами.
11. Штатные тесты и новая test suite проходят; frontend production build успешен.
12. Существующий сценарий «Оценка» продолжает работать.

## 19. Фазы реализации

Выполняй последовательно, сохраняя проект запускаемым после каждой фазы:

1. **Стабилизация и безопасность** — исправление критических дефектов, миграционная база, общий permission service.
2. **Входы** — выбор «Оценка/Контроль», каскад, безопасный первый вход, новые роли.
3. **Настройки и журнал импортов** — новые вкладки, слоты файлов, preview/status/errors.
4. **Импорты и модель истории** — база, ежедневный учёт, пользователи, распределение, исторические реестры.
5. **Экономист и Администрация** — ЧТС, новые сотрудники, смена прораба, архив.
6. **Начальник участка и Руководство** — закрытость промежуточных оценок, Свод и переводы.
7. **Экспорты** — полный Excel, диапазоны, пакет PDF/ZIP.
8. **Выпуск** — оптимизация запросов, тест параллельности, Windows, HTTPS, Android, документация восстановления.

После каждой фазы запускай релевантные тесты. Не накапливай неработающий большой пакет изменений до самого конца.
